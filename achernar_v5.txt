Purpose
Achernar should use the strongest validated perception model that a local machine can execute
reliably within its operational budget. Small models form the minimum deployment tier. More
capable hardware can qualify higher-capacity variants without changing the physical meaning of
observations or the authority of the control and safety layers. This is an edited architectural

restatement of v4, reconciled with the repository and the compute-aware runtime assessment. It
is not a byte-for-byte recovery of the unavailable v4 LaTeX source. Proposed APIs, configuration,
model tiers, and hardware support are identified as design work; this document does not certify
implementation or measured performance.

1 Executive Summary

Achernar combines an on-site Rust daemon, a React operator interface, a Tauri desktop shell, and
a Django cloud platform. Hardware access, local acquisition, measurement, and safety decisions
belong to the daemon. Cloud services support archiving, coordination, training, and analysis
where implemented. The local observing path must remain useful without a network connection.
The central v5 change is a compute-aware runtime for scalable perception. The runtime inventories
installed artifacts, identifies the execution providers available in its build, validates deployed
behavior, benchmarks eligible candidates, and chooses a qualified implementation for each model
family. Hardware discovery supplies an initial prior; quality evidence and measured resource
constraints determine the selection.


1.1 Scope and design status

The words must and shall in proposed sections specify acceptance requirements for future
implementation. They do not imply that a module, endpoint, or trained model already exists.
Current behavior is grounded in the working repository as inspected on the revision date. Dated
audits remain historical records, and the source code and migrations determine the current
executable contract.

  Area                      Status at this revision
  Classical vision          Implemented HFR, background, source rejection, and trailing
                            measurements. Unknown physical quantities remain unavailable
                            where they cannot be measured honestly.
  FQE inference             Implemented optional shadow ONNX path, 64-pixel star crops,

1.2 Target users and deployment principle

The same daemon architecture serves field equipment, backyard rigs, personal laptops, and
observatory workstations. A computer with more available compute may qualify a larger or
higher-resolution perception model. Executing unchanged weights faster does not improve those
weights’ prediction quality. Additional quality must come from a trained and validated variant,
additional useful observations, or a validated ensemble.

2 System Architecture Overview

2.1 Architecture layers

The equipment layer contains cameras, mounts, focusers, wheels, and sensors. The daemon owns
device connections, acquisition, local storage, shared perception, arbitration, and control. The
client layer displays authoritative daemon state and sends commands through a documented
transport. The cloud layer provides remote coordination and optional data services. External
weather, catalog, and astrometric resources require explicit freshness and availability handling.


              Desktop / browser client                         Optional Django platform
          Operator intent and truthful status                   Relay, archive, training




                    Local daemon                          Compute-aware runtime (proposed)
          Acquisition and shared perception                Qualified family implementations




           Controller, arbiter, safety guard                   Drivers and equipment
          Bounded proposals and ownership                 Observed outcomes and verification


The drawing shows responsibilities, not independent authority. A model runtime never sends
motor, exposure, filter, or mount commands. A larger model supplies a potentially better estimate
through the same family contract.


2.2 One product, several qualified deployments

Perception families can use different tiers on one machine. For example, FQE may run a larger
network while COC remains on a small network and the background estimator remains classical.
Per-family selection is subject to a joint resource budget: qualifying each family in isolation is
insufficient if their simultaneous memory or compute demand exceeds the observing budget.


3 Equipment Layer

3.1 Capabilities and hardware qualification

The design retains the v4 camera, mount, focuser, filter-wheel, and environmental sensor cat-
egories, including OLS/vendor SDK paths, Alpaca, and planned INDI or direct interfaces. A
declared Rust driver enum or an architectural diagram is not evidence that a device has a working
driver. Publish capability availability, connection state, and disabled reasons from the actual
implementation.
Per-rig profiles hold measured travel bounds, backlash, settling time, optics, pixel size, filter offsets,
and sensor calibration. Unknown position, temperature, tracking, or pointing is represented as
unknown. Do not synthesize zero positions or safe states to fill a UI or a model feature vector.

3.2 Compute and equipment are separate capabilities

An accelerator can improve image analysis without adding support for a camera or motor. Device
access must be tested separately from inference provider support. Release records identify OS,
architecture, native dependencies, driver/SDK versions, and actual equipment exercised.


4 Achernar Daemon: Rust and C++ Core

4.1 Hardware abstraction

Rust coordinates asynchronous work and exposes typed device operations. The C/C++ bridge
and supported OLS drivers handle the native hardware interfaces. Ownership and movement
validation remain between action proposals and drivers. Recovery must distinguish disconnection,
unsupported capability, timeout, and an unknown result after a partially completed command.


4.2 Image processing engine

Acquisition, calibration, source measurement, preview rendering, and optional stacking have
different data and timing requirements. Preserve raw science assets and record the lineage of
derived previews and measurements. A display stretch must not become the input to physical
flux measurement unless that input is explicitly part of a validated analysis contract.
Compute reservations include debayering, encoding, stacking, storage, and camera I/O. Accel-
erator memory reported as free at one instant is not an operational allocation guarantee. The
runtime must leave configured headroom for these other consumers and the operating system.


4.3 Local AI/ML processing

v5 requirement; implementation pending. Agents request a semantic model family. A
runtime handle binds the selected artifact, provider, preprocessing, postprocessing, and calibration.
Hardware-specific code lives below this handle. Classical algorithms remain available when a
learned candidate is absent, unqualified, or unhealthy.
Current implementation. FQE creates its own ORT session in achernar-daemon/src/
vision/fqe_runner.rs; application state stores a single fqe_runner. The new runtime will
replace this wiring in a later code change. The generic OnnxRunner is currently a stub.


4.4 Control systems

Sequence control, classical autofocus, drift advice, exposure policies, and future filter/mount
agents consume observations with explicit freshness, validity, and units. Motion and exposure de-
cisions retain bounded travel, ownership locks, settle periods, and outcome verification. Resource
selection does not change an agent’s autonomy mode.


4.5 Local storage

SQLite migrations define executable schemas; immutable frame assets preserve acquisition
provenance. Mutable rig state, runtime benchmarks, provider engine caches, and selection history

4.6 Daemon server

Current implementation. Axum exposes local HTTP routes under /api/v1, telemetry under

5.2 Core data and provenance

Existing migration families cover sessions, equipment, focus runs, filter/mount records, frame
assets, focuser scale, environment logs, and grouping keys. New runtime records will extend

these schemas through migrations; this document does not provide replacement SQL to apply to

Every scientific observation must be traceable to the acquired frame or frame generation that
produced it. Proposed runtime provenance adds family, variant, artifact digest, preprocess-
ing/postprocessing identifiers, provider and options, actual provider placement, precision, input
profile, batch size, calibration, selection epoch, and latency. Keep these fields separate from the
scientific value so downstream control remains independent of implementation details.


5.3 Errors and recovery

Model absence or initialization failure degrades to a qualified baseline. Corrupt artifacts are
quarantined. Non-finite predictions, mismatched tensor contracts, stale observations, and invalid
uncertainty must not produce an apparently valid measurement. Failure emits a reason and a
null/unavailable prediction; it does not fabricate zero HFR, zero uncertainty, or certainty of clear
sky.
A timeout on an asynchronous wrapper does not necessarily cancel native inference. Bound the
worker queue, prevent overlapping abandoned jobs, and discard late results by frame ID and
selection epoch. If a provider cannot be interrupted, reserve enough resources for recovery or
isolate it in a restartable worker. Do not block hardware abort paths behind a model session
lock.


5.4 Configuration

Current implementation. The operational example is achernar-daemon/achernar.example.
toml. Its current parser has no top-level [ai] section. Focus model paths live under
[focus.models]; drift tuning lives under [focus.drift].
The following is a proposed configuration contract, not runnable configuration:
[ai]
model_selection = "auto"
compute_budget = "balanced"         # efficient | balanced | quality

[ai.focus_quality]
model = "auto"              # future explicit variant pin also permitted
# Initial rollout remains shadow-only under existing control authority.


Policies adjust resource preferences within hard limits. quality cannot bypass promotion,
memory reserves, validity, or deadlines. Pins select among qualified candidates; they cannot
turn reference weights into an autonomous controller. Separate documented development-only
explicit-path loading from the production selection policy.

6 AI/ML System Design

6.1 Design principles

Preserve raw science data; attach uncertainty to estimates with a stated meaning; retain classical
operation; expose failure reasons; evaluate by rig and observing condition; keep control authority
independent of model capacity. Local learning and feedback must retain provenance and must
not silently replace promoted artifacts during an observing session.


6.2 Live image intelligence

6.2.1 Focus quality

FQE estimates physical HFR and predictive uncertainty. Current inputs are normalized per-star
crops and outputs are pooled in log-HFR space. Do not reintroduce the uncalibrated reciprocal
sharpness_score used by older examples. A larger crop, higher input resolution, or ensemble is
a new scientific variant and requires evidence on the same evaluation population.


6.2.2 Background and SNR

The classical estimator is always available. A future neural path may estimate noise maps or
quality, but must not silently denoise raw images used for scientific measurements. Calibration
of gain, read noise, black level, and saturation remains necessary regardless of GPU capacity.


6.2.3 Trailing and elongation

Classical source shape measurements provide the baseline. A future small CNN may resolve
ambiguous cases; larger models are justified only when their incremental scientific benefit is
demonstrated. Elongation direction in image coordinates is not automatically a mount RA/Dec
diagnosis without a validated coordinate mapping and adequate supporting telemetry.


6.2.4 Cloud and obstruction

COC is a candidate scalable family with a strongly data-limited quality ceiling. Thin cirrus,
moonlight, dew, contrails, gradients, and partial obstruction need representative labels. Current
heuristic cloud indicators are not a promoted learned classifier or an independent weather
interlock.


6.2.5 Focus drift

FDF remains a CPU state estimator. It learns rig-specific drift from verified focus outcomes and
temperature observations. Its quality depends on calibration, temperature coverage, and time
history rather than a larger GPU.


6.3 Settings and exposure recommendation

Rules and small contextual bandits can propose exposure/gain actions after appropriate data
collection and policy evaluation. Updates happen at permitted sequence boundaries. Their

6.4 Planning and target ranking

Visibility, horizon, moon separation, target integration requirements, and switching costs feed
deterministic scheduling or optimization. Planning can run locally or in a cloud service, but an
offline cached plan must remain interpretable and subject to local safety checks.


6.5 Post-capture analytics

Quality review, anomaly detection, retrieval, and archive analysis are separate from live actuation.
Record whether a quality label is a classical measurement, model estimate, operator label, or
composite policy result. A model should not validate itself against its own automatically accepted
outputs.


6.6 Tri-modal embedding and AstroM3Edge

AstroM3 integration and the proposed image/telemetry edge retrofit are distinct deployments.
The actual model configuration determines embedding dimension and modality contracts; the
historical v4 256-dimensional example is not a universal wire format. Future edge encoders may
scale, but retrieval compatibility requires a versioned common embedding space or an explicit
validated projection. Arbitrary dimension changes cannot remain invisible behind the same
semantic API.


6.7 Model deployment and lifecycle management

6.7.1 Identity and artifact boundaries

The runtime separates six concepts:

1. Family: a scientific task with a stable typed output, such as FQE.
2. Variant: a trained architecture and input strategy, such as a 64-pixel mobile backbone or a
   multiscale larger encoder.
3. Deployment artifact: immutable weights, numerical format, tensor schema, preprocessing,
   postprocessing, calibration, and provenance.
4. Runtime candidate: an artifact plus execution provider, provider options, and an admitted
   input/batch profile.
5. Local qualification: measured correctness, latency, and resource evidence for that candidate
   on a specific runtime stack.
6. Selected instance: the active candidate handle and its selection epoch, operating mode,
   fallback, and health.

Model parameters are not retrained for every graphics card. A finite set of artifacts can be
evaluated on many machines. Device-specific engine compilation and local benchmarking are
separate from scientific training.

6.7.2 Manifest and trust

Manifest v2 will identify family/contract version, variant, artifact version, weights digest, member-
file digests, precision, input/output schema, pre/post contracts, calibration, training lineage,
frozen evaluation manifest, quality profile, lifecycle policy, and minimum runtime requirements.
The bundle digest must bind preprocessing and calibration as well as weights. Promotion and
revocation are separate attestations bound to that digest; they do not mutate the verified bundle.
Replacing calibration or quality evidence creates a new bundle identity and invalidates affected
qualification records.
Provider declarations express tested or intended compatibility; a successful local probe is still
required. A hash verifies integrity against a trusted manifest, not the authenticity of a manifest
downloaded alongside the weights. Any future model distribution channel needs an explicit
trust root, signed manifest policy, atomic installation, revocation, and rollback rules. The first
implementation may restrict itself to operator-installed local bundles.


6.7.3 Orthogonal states


  Dimension                    States and interpretation
  Artifact lifecycle           Reference, shadow, promoted, retired, revoked. Controls
                               scientific approval and permitted use.
  Local installation           Absent, present, verified, quarantined. Describes local files and
                               integrity.
  Runtime qualification        Unbenchmarked, eligible, ineligible, stale. Applies to one
                               candidate under one runtime fingerprint and workload profile.
  Activation                   Inactive, selected, fallback. Identifies runtime use; it never
                               grants autonomy by itself.


Reference weights are test fixtures. A shadow artifact may be evaluated and logged without
controlling hardware. An artifact must be promoted and locally qualified before being considered
for autonomous use, and the controller must separately permit that authority. Current FQE
remains shadow-only even if a bundle declares a promoted state.


6.7.4 Compute profile and execution-provider probe

Inventory CPU architecture/ISA, logical and physical cores where available, memory, accelerator
identity, and power configuration. Enumerate providers present in the actual binary/runtime
installation. Probe session construction, operator compatibility, memory allocation, and a golden
vector.
Distinguish requested provider from actual graph placement. Partial execution on CPU or silent
fallback must be observable and benchmarked as that mixed candidate. A machine with a GPU
but without a compatible provider remains on an eligible CPU or classical path. CoreML and
Metal are not interchangeable provider names; backend-specific implementation details belong to
the release matrix.

6.7.5 Eligibility and preference

For family f , candidate c, deployment fingerprint d, and workload w, define the admissible set
                 Ef (d, w) = {c : integrity(c) ∧ contract(c) ∧ qualityf (c)
                                  ∧ permission(c, mode) ∧ parity(c, d)
                                  ∧ L95 (c, d, w) ≤ Df ∧ tail_policy(c, d, w)
                                  ∧ memory_reserve(c, d, w) ∧ qualified(c, d, w)}.
Df is a subsystem budget derived from the complete observing schedule. It is not a universal 50
ms limit. p95 admission alone does not guarantee every deadline; record p99, miss frequency,
maximum observed latency, and downstream observation age. These are operational SLOs on a
general-purpose OS, not a proof of hard real-time scheduling.
Preference uses a versioned family-specific quality policy evaluated on the same frozen split.
Minimum accuracy, calibration, and critical-slice gates apply before resource preferences. Among
non-dominated candidates, efficient favors lower resource cost, balanced reserves comfortable
headroom, and quality accepts higher cost within hard limits. Use explicit tie-breakers and
report the selection reason. A generic unqualified quality scalar is insufficient.
When several families share an accelerator, enforce joint memory reservations and a scheduling
budget, then verify the selected combination under concurrent load. Shared/unified RAM must
be counted once in the system memory envelope, not once as RAM and again as independent
VRAM.


6.7.6 Benchmark method

Benchmarks use representative captured or public test fixtures whose use is permitted. FQE
fixtures cover realistic crop counts, star quality, bit depth, and input shapes. Keep correctness
fixtures separate from performance fixtures where necessary, and keep model-quality test labels
out of runtime tuning.
Measure preprocessing, CPU-to-device transfer, queue wait, session execution, device-to-CPU
transfer, aggregation, and publication. Report both component timings and complete result age.
Record session/engine creation separately; exclude warmup from steady-state percentiles but
retain it as startup cost. Run candidates sequentially with memory released or accounted for
between trials. State run duration, sample count, percentile estimator, thermal/power state, and
workload profile; do not present a short run’s p99 as an all-night guarantee.
Use cold/startup, warm idle, representative co-load, and sustained profiles. The sustained profile
must be long enough to observe the target’s stable operating state and documented thermal
behavior. If a sensor is unavailable, record unknown rather than a passing thermal result.
Background qualification must yield to active acquisition and control.

6.7.9 Health, degradation, and switching

Initial implementation pins the selection. Inference faults still produce immediate unavailable
results and classical fallback. A later phase adds conservative dynamic demotion after repeated
SLO violations, with hysteresis, minimum dwell time, and a clear event. Do not opportunistically
promote a model midway through autofocus or an exposure transaction.
Validate a replacement before an atomic switch at a safe boundary. Account for the temporary
memory overlap of old and new sessions; warm standby is optional when memory permits, not a
universal requirement. Carry a selection epoch with each result so late outputs cannot overwrite
newer observations. Pin one measurement contract across an autofocus curve or restart its
comparison window after a model change, because calibrated variants can still have different
residual biases.


6.7.10 Evidence and limits

MobileNetV3 and EfficientNet support capacity families; Jacob et al. support validated precision-
specific deployment[1, 2, 3]. MnasNet and NetAdapt support measured latency rather than
FLOP-based selection[4, 5]. MLPerf Mobile and ML-EXray motivate whole-stack measurement
and deployed parity[6, 7]. Research on resource-aware adaptation supports later switching[8, 9],
while SBC experiments motivate recording power configuration[10]. None establishes Achernar-
specific tiers, memory budgets, or accuracy gains. Those require Achernar data and hardware
validation.

Retain the v4 progression: classical baseline, learned perception, logged proposal, supervised

v5 requirement; implementation pending. The supervisor will manage autonomy modes

7.8 Focus controller algorithm

Current implementation. The operating focus path uses a classical sweep and fit with fresh

not a post-move measurement. FQE predictions are shadow measurements. The bounded AI
offset loop remains subject to training, replay, and control-promotion work.
The future loop captures a baseline, validates the observation, obtains an offset proposal, checks
uncertainty and ownership, clamps travel, moves and settles, measures a fresh frame, and tests
improvement. It reduces step size or falls back to a classical bracket/curve fit when improvement
is absent. Total travel, duration, failed-improvement count, and uncertainty cap the run. Do
not reuse stale inference after motion, filter change, stream restart, or a model-selection epoch
change. The completed bounded controller must acquire a fresh optical sample after moving to
its chosen optimum before declaring verified focus quality; successful motor-command completion
alone is insufficient.

9 Data Engineering and Labeling

9.1 Classical labels and measurement lineage

Use classical HFR, source masks, background, and elongation as documented labels or features,
retaining raw and derived asset references. Label precision and measurement failures set a ceiling
on what supervised training can infer. Include failed autofocus runs and invalid conditions with
explicit labels or exclusion reasons.


9.2 Weak labels

Rules for cloudy, saturated, trailed, or accepted frames are useful weak supervision. Store the rule
version and disagreement with human review. Acceptance decisions produced by the incumbent
model require safeguards against a feedback loop that excludes its own failure cases.


9.3 Public archives

Survey images, light curves, and spectra may support pretraining or retrieval experiments.
Dataset licensing, acquisition system, pixel scale, noise model, and observing distribution must
be recorded. Survey success is not evidence of performance on a consumer camera or an amateur
optical train.

9.4 Augmentation

10 Metrics

10.1 Local perception quality and runtime

Maintain independent quality and runtime reports. Quality reports use common frozen data,
calibration and slice gates. Runtime reports use the exact deployment fingerprint and workload.
Store reproducible methodology, sample counts, confidence/coverage evidence, and the decision
policy version.
At the 1–5 Hz design cadence, one interval is 1000–200 ms. This interval includes more than
ONNX execution. Derive per-family deadlines from acquisition, classical processing, queueing,
inference, publication, and safety headroom; no arbitrary percentage is certified here. Monitor
observation age and missed deadlines through the entire path.


10.2 Recommendation metrics

Evaluate exposure and filter policies against a documented baseline using appropriate logged
propensities and off-policy methods where applicable. Report uncertainty and support limitations;
a biased historical log cannot prove a new policy’s safety or superiority.


10.3 System-level outcomes

Track focus convergence and duration, final image quality, retained integration, false interruptions,
fallback frequency, recovery success, and user overrides. Resource telemetry includes latency
distributions, memory peaks, thermal state where available, and contention. Telemetry explains
performance without becoming an unbounded recording workload.

12 Local and Cloud Responsibilities

12.1 Local operation

Acquisition, physical measurements, qualified inference, arbitration, safety, and offline logging
remain local. A high-capacity workstation model can still be a local model. “Local” describes
placement and availability, not a fixed maximum parameter count or a universal precision.


12.2 Cloud operation

Training, archive-scale analysis, optional retrieval, model distribution, and coordination can use
cloud resources. Network failure must not interrupt the required local baseline. Cloud advice
or downloaded models do not bypass local authorization, promotion, runtime qualification, or
equipment constraints.


13 Network Layer

Retain local connectivity, optional VPN/remote access, and the daemon-to-cloud relay design.
Claims of WiFi access-point setup, WebRTC/TURN, or specific latency must reflect actual
deployed components. Bound reconnect retries, detect stale remote state, and distinguish
accepted command from confirmed hardware completion. Model downloads and uploads should
be scheduled so they do not interfere with acquisition or storage throughput.


14 Web Platform and Operator Experience

14.1 Control and data planes

The current React client and Tauri shell share an operator interface; Django supports remote
transport where wired. The daemon is the authority for live equipment capability and status.
Local HTTP, telemetry, and relay payloads must agree on missingness, command identity, and
error meanings.


14.2 Runtime status experience

v5 requirement; implementation pending. The UI shows selected family/variant, operating
mode, reason, baseline, and health. Normal users choose efficient, balanced, or quality; advanced
diagnostics can reveal provider placement, memory, benchmark age, and rejection reasons.
Explain why a larger model is unavailable without requiring users to interpret CUDA operator

15 Pragmatic Requirements

 1. Preserve raw assets and measurement lineage.
 2. Start with a working classical baseline and honest unavailable values.
 3. Spend extra compute only where measured quality improves.
 4. Qualify exact artifacts and deployed pipelines on the target device.
 5. Keep promotion, local performance qualification, and control authority separate.
 6. Bind normalization, units, aggregation, calibration, and weights together.
 7. Protect camera/control headroom and validate concurrent workloads.
 8. Retain grouped data splits, difficult slices, and failed-run evidence.
 9. Make fallback, provider placement, and selection reasons observable.
10. Preserve rollback and require live shadow evidence before actuation.


16 Implementation Roadmap and Acceptance Gates

16.1 Phase 0: Contracts and documentation

This revision establishes the editable v5 source, a detailed runtime ADR, documentation status
corrections, and a dated review addendum. It does not implement provider loading or change
production model selection.


16.2 Phase 1: FQE runtime foundation

Implement manifest parsing and legacy shadow migration, complete candidate inventory, CPU
provider probing, golden parity, benchmark/cache records, family handles, and read-only status.
Keep classical authority and existing batched inference. Test reference artifacts as fixtures
without claiming quality improvement. Acceptance: unavailable/corrupt models cannot prevent
baseline operation, stale caches cannot qualify a changed candidate, and all selection/rejection
reasons are inspectable.


16.3 Phase 2: Scientific variant evidence

Train Nano and one larger FQE variant on common real-data splits. Calibrate and compare
task quality, coverage, and hard slices. Publish shadow artifacts and validate deployed parity.
Acceptance: the larger variant demonstrates useful improvement and both satisfy minimum
quality; promotion remains an explicit evidence-backed decision.

16.4 Phase 3: Accelerator release qualification

Package a tested NVIDIA Linux path and separately qualify Jetson aarch64. Exercise cold setup,
engine cache, sustained and co-load performance, resource exhaustion, provider failure, and
actual graph placement. Acceptance: release records identify exact device/runtime combinations

evidence.


16.5 Phase 4: Additional families

COC follows after a real corpus and executable model. Extend shared budgets and concurrent
qualification. TED and neural BGE follow demonstrated task value and scientific integrity checks;
AstroM3Edge remains a future integration.


16.6 Phase 5: Dynamic degradation

Implement sustained-violation detection, hysteresis, safe switching, memory overlap handling,
epoch validation, and observation expiry. Acceptance: no model oscillation under transient
load, no mixing of stale results across epochs, and no unbounded native work after a timeout.
Opportunistic promotion during a critical observing transaction remains excluded.
