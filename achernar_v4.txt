System Architecture, AI/ML Design, and Autonomous Control Specification

Abstract
Achernar is a unified astronomy imaging and control system for amateur and professional
astronomers, providing a fluid offline-to-online experience. The platform centers on a
lightweight cross-platform daemon written in Rust that interfaces directly with USB-connected
astronomy hardware.
This document presents the full system architecture, hardware interfaces, processing
pipelines, AI/ML components with reliability features, and—new in this revision—a complete specification for closed-loop AI-driven hardware control. Achernar’s hybrid AI architecture runs quantized ONNX models at sub-50 ms latency on the edge for focus scoring, cloud
detection, and direct hardware parameter control, while the cloud hosts a novel tri-modal
embedding space (Image, Time-Series, Spectra) for recommendation engines and anomaly
detection. The AI Parameter Control Layer formalizes the transition from AI-advisory to
bounded autonomous operation via a deterministic safety supervisor, action arbiter, per-rig
device profiles, and shadow-mode evaluation infrastructure.

1

Achernar System Architecture

Executive Summary

Achernar is a unified astronomy imaging and control system designed to support both amateur
and professional astronomers through a fluid offline-to-online user experience. The platform
consists of a lightweight, cross-platform daemon written in Rust that interfaces directly with
USB-connected peripherals such as astrophotography cameras and telescope mounts.
This daemon enables real-time frame capture, high-speed I/O, hardware-accelerated debayering
and video encoding (H.264/MJPEG), and execution of compact ONNX-based AI models that
dynamically score focus, suggest optimal exposure and gain, and recommend filter choices—all
without requiring an internet connection.

1.1

Key Features

 Offline-First Design: Full functionality without internet connectivity
 Edge AI Processing: Real-time focus scoring, cloud detection, and imaging recommendations
 Closed-Loop AI Control: AI models govern focuser, exposure, and filter parameters
within deterministic safety bounds
 Hardware Acceleration: GPU-accelerated image processing and video encoding when
available
 Multi-Platform Support: Web interface, desktop application, and mobile PWA
 Professional-Grade Calibration: Automatic dark, flat, and dark-flat frame integration
 Cloud Synchronization: Automatic session sync when connectivity is restored
 Uncertainty-Aware AI: All predictions include confidence scores for reliable decisionmaking
 Active Learning: User feedback continuously improves model performance

1.2

Target Users

 Casual Users: Backyard astronomers using a browser-based web interface
 Professional Astronomers: Remote observatory operators in low-connectivity environments
 Students & Researchers: Educational institutions and field-deployable research setups
 Individual Enthusiasts: Users running the system on personal laptops

2

System Architecture Overview

The Achernar system is designed with a layered architecture that separates concerns between
hardware interfacing, data processing, AI/ML inference, user interfaces, and cloud services.
This design enables both edge computing for real-time operations and cloud computing for
collaboration, archiving, and large-scale model training.

2.1

Architecture Layers

1. Equipment Layer: Physical hardware devices (cameras, mounts, focusers, filter wheels,
sensors)
2. Daemon Layer: Rust-based core with hardware abstraction, image processing, AI inference, and the AI Control Layer
3. Network Layer: Local WiFi AP, internet connectivity, and VPN tunneling
4. Client Layer: Desktop applications, web browsers, tablets, and mobile devices
5. Cloud Platform: Django-based web services with AI/ML infrastructure
6. External Services: Weather APIs, astronomical catalogs, and astrometry services

Achernar Daemon (Rust + C++ Core)

The daemon is the heart of the Achernar system, providing hardware abstraction, real-time
image processing, AI inference, and—with the AI Control Layer—closed-loop parameter control.

4.1

Hardware Abstraction

 USB API: libusb 1.0, tokio-serial, hidapi-rs
 INDI Layer: INDI client (Rust), libindi bindings, TCP async
 Camera Drivers: Camera SDK bindings, FFI to C++, USB async I/O

4.2

Image Processing Engine (C++/OpenCV + Rust)

 Raw Buffer: cv::Mat + ndarray, FITS (fitsio-rs), TIFF (image-rs), shared memory
 Calibration: OpenCV algorithms, dark/flat processing, Rust orchestration, libraw bindings
 Alignment: Feature detection (AKAZE/ORB), opencv-rust, RANSAC matching
 Stacker: C++ core, Rust threading, tokio async, memory-mapped operations
 Post-Processing: Histogram stretch, C++ processing, Rust coordination, GPU acceleration

4.3

AI/ML Edge Processing (ONNX Runtime)

Compact AI models run locally for real-time guidance with uncertainty quantification and
explainability. With the AI Control Layer described in Section 7, these models now also drive
hardware parameters directly within deterministic safety bounds.

4.4

Control Systems

 AI Recommender: Contextual bandit (LinUCB/Thompson), Bayesian updates

6

AI/ML System Design

6.1

Design Principles

1. Scientific Integrity First: Never alter raw science data with ML
2. Uncertainty-Aware: All predictions include confidence scores
3. Explainable Decisions: Critical recommendations show reasoning
4. Graceful Degradation: System works without AI; AI enhances, does not replace classical methods

7

AI Parameter Control & Closed-Loop Hardware Autonomy
Design Note
This section represents the evolution of Achernar from an AI-enhanced observation system to a closed-loop autonomous control system. Every controllable subsystem is formalized as: observe → estimate state → choose action → enforce safety → actuate → verify
outcome.

7.1

Control Philosophy

The key shift is that AI models no longer only score images or recommend parameters—they
drive hardware parameters in real time within a stack of safety guarantees. Two paradigms are
distinguished:
AI-Assisted Control (primary production mode). AI infers state and proposes parameters; a deterministic controller executes them within auditable safety bounds. Predictable,
debuggable, hardware-safe.
End-to-End AI Control (research mode, deferred). AI directly outputs hardware commands. Dangerous on expensive hardware without extensive simulation-first training. Deferred
until a simulation environment and offline replay harness are mature.
Important
The correct development order is: (1) classical baseline, (2) AI perception, (3) AI proposal,
(4) AI parameter tuning in bounded mode, (5) optional RL in simulation only. Do not
start with RL on physical hardware.

7.2

Formal Control Specification per Subsystem

Each controllable subsystem is treated as a constrained controller:
 ot — Observation: frame, focuser position, temperature, filter, history
 st — Latent state: true optical focus error, backlash state, thermal drift trend
 at — Action: move focuser ±n steps, change exposure, switch filter, pause imaging
 C/R — Cost/Reward: lower HFR better, fewer moves better, hitting hard stop catastrophic
 Constraints: travel range, ownership locks, confidence thresholds, settle timing

Model 5: Trailing / Elongation Detector (TED)

Purpose. Detect guide failures, wind buffeting, and mount tracking errors that elongate stars,
enabling the system to shorten exposure or recalibrate the guider.
Classical component (primary).
1. Source extraction: SEP (C backend), minimum area 5 px, detection threshold 3σ

Split Strategy

Important
Never use random row-level splitting. Multiple samples from the same run in both train
and test sets constitutes severe data leakage. Split by run and date.
Oldest 70% of runs → train; next 15% → validation; newest 15% → test. Hold out one or more
rigs entirely for a generalization evaluation set.

Bounded AI Autofocus (Production MVP)

Phase 1 — Baseline Capture
Acquire preview at current position. Compute classical HFR and AI quality score.
Verify sufficient stars. Abort to classical fallback if observation quality is poor.
Phase 2 — Offset Prediction
Run focus offset model; obtain delta steps and uncertainty steps.
Phase 3 — Predicted Move
Propose delta steps; clamp through safety guard; apply backlash compensation if
direction changed; move focuser.
Phase 4 — Measure Improvement
Settle → acquire preview → recompute metrics → compare against prior state.
Phase 5 — Local Refinement
If improved: continue with smaller bounded steps. If not improved: reverse or switch
to bracket search.
Phase 6 — Convergence Decision
Stop when improvement < ε over N steps, HFR plateaus, uncertainty too high, retry
budget exhausted, or travel budget exhausted.
Phase 7 — Classical Fallback
Run classical bracket + parabola fit around predicted optimum region.
7.8.2

Classical Fallback

Sample {−60, −30, 0, +30, +60} steps around initial position. Fit parabola or robust V-curve.
Choose estimated optimum; confirm with 1–2 local refinement points. Bracket width is adaptive:
high uncertainty ⇒ wider bracket; low uncertainty ⇒ narrow refinement.

resuming imaging).

8.3

Mount Subsystem

The mount controller is the most safety-critical subsystem in the entire system. A miscommunication here can slew into an obstacle, collide with a pier, or leave the mount unparked in deteriorating weather. All ML components in this subsystem operate in advisory or parametertuning roles only; raw slew commands always pass through a deterministic safety layer.
Important
The mount safety guard must enforce hard-coded altitude limits, meridian flip windows,
and pier collision zones derived from the rig geometry profile. No ML model is permitted
to bypass these. The mount controller maturity ladder starts at L2 (AI Proposal) for
parameter tuning and never proceeds to L3 (Bounded Autonomy) for slew commands
without explicit user configuration and hardware interlock confirmation.

15

Pragmatic Cautions

1. Never denoise raw subs with ML—preserve raw science integrity
2. Always keep classical fallback available—never ship ML without it
3. Make edge models tiny—test latency on target hardware early
4. Calibrate all probabilities—uncalibrated confidence is worse than none
5. Shadow mode before any bounded autonomy—non-negotiable
6. Do not start with RL on physical hardware—build offline replay first
7. Beware feedback loops—periodically surface random samples, not only AI-curated
data
8. Test on representative rigs—backyard setup ̸= desert observatory
9. Explain failures loudly—build trust through transparency
10. Measure operational metrics—convergence rate matters more than model accuracy
